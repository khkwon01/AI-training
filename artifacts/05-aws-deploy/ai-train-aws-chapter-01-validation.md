# ai-train Module 04: AWS에 올리고 결과 확인하기

## 이 장에서 배우는 것

- 배포가 왜 필요한지
- 작은 Python 프로그램을 AWS에 올린다는 것이 무엇인지
- 배포 후 무엇을 확인해야 하는지
- 성공과 실패를 어떻게 구분하는지

## 먼저 쉬운 설명

프로그램을 내 컴퓨터에서만 실행하면,  
그 프로그램이 다른 환경에서도 잘 동작하는지 알기 어렵다.

그래서 작은 프로그램이라도 한 번 배포해 보면:

- 실제로 실행되는지 확인할 수 있고
- 필요한 설정이 무엇인지 알 수 있고
- 문제가 생겼을 때 어디를 봐야 하는지 배울 수 있다

여기서 중요한 것은 "복잡한 인프라 만들기"가 아니라  
"내가 만든 결과물이 실제로 동작하는지 확인하는 경험"이다.

이 장에서는 AWS의 많은 기능을 다 외우지 않는다.  
대신 아래 한 가지 질문에 답할 수 있으면 충분하다.

`내 프로그램이 AWS에서 정말 실행되고 있는가?`

## 핵심 개념

### 1. 배포

내 컴퓨터 밖의 환경에서 프로그램을 실행할 수 있게 올리는 것이다.

### 2. 검증

배포가 끝났다고 끝이 아니다.

아래를 확인해야 한다.

- 프로그램이 실행되는가
- 원하는 결과가 나오는가
- 문제가 생기면 로그를 볼 수 있는가

### 3. 되돌리기

문제가 생겼을 때 이전 상태로 돌아갈 수 있어야 한다.

## 오늘 사용할 아주 작은 시나리오

초보자는 복잡한 서비스보다 한 번에 확인 가능한 작은 예시가 좋다.

이번 장에서는 아래 같은 상태 확인용 Python 서비스를 떠올리면 된다.

```python
def health():
    return {"status": "ok", "message": "hello from aws"}
```

이 예시에서 우리가 확인할 것은 세 가지뿐이다.

- 요청을 보냈을 때 응답이 오는가
- `status` 값이 `ok`인가
- 실패하면 어디서 원인을 찾을 수 있는가

## 따라 하기

### 실습 1. 배포 목적 정하기

작은 Python 프로그램 하나를 고른다.

예:

- 간단한 점수 계산 API
- 짧은 CLI 결과를 보여주는 서비스
- 상태 확인용 `health` 응답 서비스

### 실습 2. 배포 방식 비교하기

- container 방식: 조금 더 구조적이지만 준비가 더 필요할 수 있다
- serverless 방식: 작고 단순한 기능에는 더 가볍게 시작할 수 있다

초보자 입장에서는:

- 아주 작은 기능이면 serverless
- 앱 구조를 보여주고 싶으면 container

처럼 생각하면 이해가 쉽다.

이번 장의 예시는 "응답이 한 번 잘 오는지 확인"하는 수준이므로  
serverless처럼 가볍게 시작하는 상황을 떠올리면 이해하기 쉽다.

### 실습 3. 확인할 것 적기

- 환경변수는 무엇이 필요한가
- 배포 후 어떤 주소나 명령으로 확인할 것인가
- 실패하면 무엇을 먼저 볼 것인가

예시:

- 환경변수: `APP_MODE=prod`
- 확인 방법: health 주소 접속 또는 간단한 요청 보내기
- 실패 시 먼저 볼 것: 배포 로그와 오류 메시지

### 실습 4. 아주 간단한 검증 시나리오 따라 적기

아래처럼 실제 확인 장면을 짧게 적어 본다.

1. 브라우저나 요청 도구로 health 주소를 연다.
2. `status` 값이 `ok`인지 본다.
3. 안 보이면 로그와 환경변수를 확인한다.

예시:

```text
확인 주소: /health
기대 결과: {"status":"ok","message":"hello from aws"}
첫 실패 확인 위치: 로그
```

### 실습 5. 워크북 한 칸 채우기

아래 빈칸을 직접 채우면, 배포 후 무엇을 확인할지 더 또렷해진다.

```text
내가 확인할 주소 또는 방법:
________________________________

성공이라고 볼 기준 한 줄:
________________________________

실패하면 가장 먼저 볼 곳:
________________________________
```

## 자주 하는 실수

- 배포만 하고 동작 확인을 하지 않기
- 환경변수를 빠뜨리기
- 로그를 어디서 보는지 모른 채 넘어가기
- 되돌리는 방법을 생각하지 않기

## 확인 체크리스트

- 무엇을 배포하는지 한 줄로 설명할 수 있는가
- 왜 그 방식을 선택했는지 말할 수 있는가
- 배포 후 확인 방법이 있는가
- 문제가 생겼을 때 어디를 볼지 알고 있는가

### 성공 체크리스트

- 요청을 보냈을 때 응답이 돌아온다
- 응답 안에 내가 기대한 값이 보인다
- 한 번 더 확인해도 같은 결과가 나온다
- 성공 기준을 다른 사람에게 한 줄로 설명할 수 있다

### 실패 체크리스트

- 주소를 열었는데 응답이 없거나 오류가 난다
- 응답은 오지만 `status` 같은 핵심 값이 기대와 다르다
- 환경변수가 빠져 있거나 잘못 들어가 있다
- 실패 원인을 찾을 로그 위치를 아직 모른다

## 쉬운 예시 시나리오

아주 작은 Python 서비스가 아래처럼 상태를 반환한다고 가정하자.

```python
def health():
    return {"status": "ok", "message": "hello from aws"}
```

배포 후에는 아래를 확인하면 된다.

- 주소에 접속했을 때 `status`와 `message`가 보이는가
- 오류가 나면 로그에 어떤 메시지가 보이는가
- 환경변수가 빠졌다면 어디서 다시 설정해야 하는가

### 이 시나리오에서 성공과 실패를 빠르게 나누는 법

- 성공 예: `{"status":"ok","message":"hello from aws"}`처럼 기대한 값이 그대로 보임
- 실패 예 1: 페이지가 열리지 않음
- 실패 예 2: `status`가 없거나 `error`만 보임
- 실패 예 3: 로그에 환경변수 관련 오류가 남음
