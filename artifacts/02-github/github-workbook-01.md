# GitHub Workbook 01
## Issue → PR 흐름 실습 — 3가지 시나리오

> 이 워크북은 직접 따라 하며 GitHub 협업 흐름을 익히는 형식입니다.  
> 각 시나리오를 순서대로 따라 하면서 빈칸을 채워보세요.

---

## 이 워크북의 목표

- 혼자 작업할 때의 Issue → branch → PR → merge 흐름을 익힌다
- 코드 리뷰를 요청하고, 받고, 반영하는 방법을 익힌다
- AI 리뷰를 GitHub 협업에 통합하는 방법을 익힌다

---

## 시작 전 체크

- [ ] GitHub 계정이 있다
- [ ] Git이 설치되어 있다 (`git --version` 실행 가능)
- [ ] 실습에 사용할 GitHub 저장소(repository)가 있다
- [ ] 터미널(또는 VS Code 터미널)을 열 수 있다
- [ ] 저장소를 로컬에 clone한 상태다

---

## Git 명령어 빠른 참조

자주 사용하는 Git 명령어 모음입니다. 시나리오를 따라 하는 중에 참고하세요.

### 저장소 준비
```bash
# 저장소 클론 (처음 한 번만)
git clone https://github.com/사용자이름/저장소이름.git

# 현재 상태 확인
git status

# 최신 변경사항 가져오기
git pull origin main
```

### 브랜치 작업
```bash
# 새 브랜치 만들고 이동
git checkout -b 브랜치이름

# 브랜치 목록 보기
git branch

# 다른 브랜치로 이동
git checkout 브랜치이름

# 현재 브랜치 확인
git branch --show-current
```

### 변경사항 저장
```bash
# 변경된 파일 확인
git status

# 특정 파일 스테이징
git add 파일이름

# 변경된 모든 파일 스테이징
git add .

# 커밋 (저장)
git commit -m "커밋 메시지"

# GitHub에 올리기
git push origin 브랜치이름
```

### 자주 쓰는 조합
```bash
# 변경사항 확인 → 스테이징 → 커밋 → 푸시 (한 번에)
git status
git add .
git commit -m "커밋 메시지"
git push origin 브랜치이름
```

---

## 브랜치 이름 규칙

좋은 브랜치 이름은 "무슨 작업인지"를 한눈에 알 수 있게 합니다.

| 작업 종류 | 형식 | 예시 |
|-----------|------|------|
| 새 기능 추가 | `feature/기능이름` | `feature/add-memo-list` |
| 버그 수정 | `fix/버그이름` | `fix/delete-button-error` |
| 문서 수정 | `docs/설명` | `docs/update-readme` |
| 리팩토링 | `refactor/설명` | `refactor/memo-function` |

**빈칸 채우기:**
```text
"메모 삭제 버튼 오류 수정" 작업의 브랜치 이름:
fix/________________________________

"사용자 로그인 기능 추가" 작업의 브랜치 이름:
________________________________/________________________________
```

---

## 커밋 메시지 규칙

좋은 커밋 메시지는 "무엇을 왜 했는지"를 담습니다.

| 유형 | 의미 | 예시 |
|------|------|------|
| `feat:` | 새 기능 추가 | `feat: 메모 저장 기능 추가` |
| `fix:` | 버그 수정 | `fix: 삭제 버튼 클릭 오류 수정` |
| `docs:` | 문서 수정 | `docs: README 설치 방법 수정` |
| `style:` | 코드 형식 변경 | `style: 들여쓰기 수정` |
| `refactor:` | 기능 변화 없는 코드 수정 | `refactor: 함수 이름 명확하게 변경` |

## 시나리오 1 — 혼자 작업: Issue → PR → Merge

### 목표
혼자 작업할 때의 전체 흐름을 순서대로 따라 해본다.

### 이 시나리오에서 할 작업
```text
README 파일에 "프로젝트 설명" 섹션을 추가하는 작은 수정
```

---

### Step 1-1. Issue 만들기

Issue는 "앞으로 할 일"을 기록하는 곳입니다.  
GitHub 저장소 → Issues 탭 → New issue 버튼을 클릭하세요.

**좋은 Issue 제목 예시:**
- `README에 프로젝트 설명 섹션 추가`
- `메모 삭제 기능 버그 수정`
- `API 엔드포인트 문서화 추가`

**Issue 작성 템플릿:**
```
제목: [작업 종류] 간단한 설명

본문:
## 무엇을 할 것인가?
(작업 내용을 구체적으로 설명)

## 왜 하는가?
(이 작업이 필요한 이유)

## 완료 기준
- [ ] (이것이 되면 완료라고 할 수 있는 것)
- [ ] (이것이 되면 완료라고 할 수 있는 것)
```

**직접 써보기:**
```text
Issue 제목:
________________________________

본문 — 무엇을 할 것인가:
________________________________
________________________________

본문 — 왜 하는가:
________________________________

완료 기준:
- [ ] ________________________________
- [ ] ________________________________
```

Issue를 저장하면 번호가 붙습니다. (예: #1, #5)

```text
내가 만든 Issue 번호: #______
```

- [ ] Issue를 만들었다

---

### Step 1-2. Branch 만들기

Issue 번호를 브랜치 이름에 포함하면 나중에 찾기 쉽습니다.

**형식:** `issue-번호/작업설명` 또는 `feature/작업설명`

```bash
# main 브랜치에서 시작
git checkout main
git pull origin main

# 새 브랜치 만들기
git checkout -b docs/add-project-description
```

직접 입력할 명령어:
```bash
git checkout -b ________________________________
```

브랜치가 만들어졌는지 확인:
```bash
git branch --show-current
```

```text
현재 브랜치 이름:
________________________________
```

- [ ] 새 브랜치를 만들었다
- [ ] `git branch --show-current`로 브랜치를 확인했다

---

### Step 1-3. 코드 수정하기

현재 브랜치에서 작업합니다.

**이번 실습에서 할 변경:**
- README.md 파일을 열어서 "## 프로젝트 설명" 섹션 추가

```text
수정할 파일 이름:
________________________________

어떤 내용을 수정했는가:
________________________________
________________________________
```

수정 후 상태 확인:
```bash
git status
```

```text
git status 결과에서 변경된 파일 이름:
________________________________
```

- [ ] 파일을 수정했다
- [ ] `git status`로 변경사항을 확인했다

---

### Step 1-4. Commit 하기

**스테이징(git add):** 커밋할 파일을 선택하는 단계
**커밋(git commit):** 변경사항을 저장하는 단계

```bash
# 변경된 파일 스테이징
git add README.md

# 커밋
git commit -m "docs: README에 프로젝트 설명 섹션 추가"
```

직접 입력할 명령어:
```bash
git add ________________________________
git commit -m "________________________________"
```

커밋 성공 시 터미널에 이런 내용이 보입니다:
```
[브랜치이름 abc1234] 커밋 메시지
 1 file changed, 5 insertions(+)
```

```text
커밋 메시지로 사용한 것:
________________________________

커밋 후 보인 결과 (요약):
________________________________
```

- [ ] 파일을 스테이징했다
- [ ] 커밋 메시지를 규칙에 맞게 작성해서 커밋했다

---

### Step 1-5. GitHub에 Push하기

```bash
git push origin 브랜치이름
```

직접 입력할 명령어:
```bash
git push origin ________________________________
```

성공하면 터미널에 이런 내용이 보입니다:
```
To https://github.com/...
 * [new branch]      브랜치이름 -> 브랜치이름
```

- [ ] GitHub에 push했다
- [ ] GitHub 웹에서 브랜치가 생성된 것을 확인했다

---

### Step 1-6. Pull Request (PR) 만들기

GitHub 웹에서 PR을 만듭니다.

1. 저장소 페이지로 이동
2. "Compare & pull request" 버튼 클릭 (또는 Pull requests → New pull request)
3. 아래 형식으로 PR 설명 작성

**PR 설명 템플릿:**
```
## 무엇을 변경했는가
(변경 내용 요약)

## 왜 변경했는가
(변경 이유)

## 관련 Issue
Closes #이슈번호

## 리뷰 요청 사항
(특별히 확인해 달라고 할 점)
```

직접 써보기:
```text
PR 제목:
________________________________

변경 내용:
________________________________

이유:
________________________________

관련 Issue: Closes #______

리뷰 요청 사항:
________________________________
```

- [ ] PR을 만들었다
- [ ] PR 설명에 목표, 이유, 관련 Issue를 포함했다

---

### Step 1-7. Merge하기

PR 페이지에서 확인 후 Merge 버튼을 클릭합니다.

**Merge 전 체크:**
- [ ] PR 설명이 변경 내용을 잘 설명하는가?
- [ ] 변경된 파일이 의도한 것만 포함되어 있는가?
- [ ] 커밋 메시지가 적절한가?

Merge 완료 후:
```bash
# main으로 돌아오기
git checkout main
# 최신 변경사항 가져오기
git pull origin main
```

- [ ] PR을 Merge했다
- [ ] `git checkout main` 후 `git pull`로 업데이트했다

---

### 시나리오 1 완료 체크

- [ ] Issue를 만들었다
- [ ] 브랜치를 만들었다
- [ ] 코드를 수정하고 커밋했다
- [ ] GitHub에 push했다
- [ ] PR을 만들었다
- [ ] PR을 Merge했다
- [ ] 전체 흐름을 말로 설명할 수 있다

## 시나리오 2 — 코드 리뷰 받기

### 목표
PR에 리뷰어를 지정하고, 리뷰 코멘트를 받고, 수정 후 re-push하는 흐름을 익힌다.

### 이 시나리오에서 할 작업
```text
시나리오 1에서 만든 변경 중 일부를 수정하고 리뷰를 요청한다.
(또는 새로운 작은 변경을 만들어서 리뷰를 요청한다.)
```

---

### Step 2-1. 새 브랜치와 변경사항 만들기

시나리오 1을 완료했다면 새 작업을 시작합니다.

```bash
git checkout main
git pull origin main
git checkout -b feature/add-usage-example
```

직접 입력할 명령어:
```bash
git checkout -b ________________________________
```

파일을 수정하고 커밋합니다:
```bash
git add ________________________________
git commit -m "________________________________"
git push origin ________________________________
```

- [ ] 새 브랜치를 만들고 변경사항을 커밋했다

---

### Step 2-2. 리뷰어 지정하기

PR을 만들 때 또는 만든 후에 리뷰어를 지정할 수 있습니다.

**GitHub 웹에서:**
1. PR 페이지 오른쪽 → "Reviewers" → 기어 아이콘 클릭
2. 리뷰를 요청할 사람의 GitHub 아이디 입력
3. 선택 완료

**리뷰어에게 요청할 내용 미리 정하기:**

좋은 리뷰 요청 예시:
```text
- 이 변경이 초보자도 쉽게 이해할 수 있는지 확인해주세요.
- 코드 설명이 충분한지 봐주세요.
- 더 간단하게 쓸 수 있는 부분이 있는지 알려주세요.
```

나쁜 리뷰 요청 예시:
```text
- 그냥 봐주세요. (너무 막연함)
- 다 확인해주세요. (범위가 너무 넓음)
```

직접 써보기:
```text
리뷰어 GitHub 아이디: ________________________________

리뷰 요청 사항 (구체적으로 3가지):
1. ________________________________
2. ________________________________
3. ________________________________
```

- [ ] PR에 리뷰어를 지정했다

---

### Step 2-3. 리뷰 코멘트 달기

리뷰어 입장에서 코멘트 다는 방법도 익혀봅시다.

**GitHub에서 코멘트 다는 방법:**
1. PR의 "Files changed" 탭 클릭
2. 코멘트를 달고 싶은 줄에 마우스를 올리면 `+` 버튼 표시
3. `+` 버튼 클릭 → 코멘트 입력
4. "Start a review" 또는 "Add single comment" 클릭

**좋은 리뷰 코멘트 예시:**
```
이 부분이 초보자에게 조금 어려울 수 있을 것 같아요.
"x가 y보다 클 때" 같은 방식으로 설명을 추가하면 어떨까요?
```

**나쁜 리뷰 코멘트 예시:**
```
이거 틀렸어요. (이유 없음)
그냥 다시 써요. (방향 없음)
```

리뷰 코멘트를 남긴 후에는 "Submit review" 에서 상태 선택:
- **Comment:** 단순 코멘트 (승인/거절 없음)
- **Approve:** 이대로 Merge해도 됨
- **Request changes:** 수정 후 다시 확인 필요

```text
리뷰 상태로 어떤 것을 선택했는가:
[ ] Comment  [ ] Approve  [ ] Request changes

이유:
________________________________
```

- [ ] 코멘트를 달거나, 리뷰어의 코멘트를 받았다

---

### Step 2-4. 코멘트에 응답하고 수정하기

리뷰 코멘트를 받으면:

**방법 1 — 코멘트에 답글 달기:**
- 동의하면: "맞아요, 수정하겠습니다!"
- 다른 의견이면: "이렇게 한 이유는 ... 때문입니다. 어떻게 생각하시나요?"

**방법 2 — 코드 수정 후 re-push:**
```bash
# 같은 브랜치에서 수정
# (파일 수정 후)
git add 수정한파일
git commit -m "fix: 리뷰 반영 — 설명 추가"
git push origin 브랜치이름
```

push 하면 PR에 자동으로 새 커밋이 반영됩니다.  
리뷰어에게 수정 완료를 알리려면 코멘트에 "수정 완료했습니다" 라고 남기세요.

직접 해보기:
```bash
# 수정할 파일 열고 수정 후...
git add ________________________________
git commit -m "________________________________"
git push origin ________________________________
```

```text
리뷰 코멘트에서 수정한 내용:
________________________________
________________________________

re-push 후 사용한 커밋 메시지:
________________________________
```

- [ ] 리뷰 코멘트를 반영해서 코드를 수정했다
- [ ] 수정 후 같은 브랜치에 re-push했다
- [ ] PR에 새 커밋이 반영된 것을 GitHub 웹에서 확인했다

---

### Step 2-5. 리뷰 완료 후 Merge

리뷰어가 Approve 하면 Merge 할 수 있습니다.

**Merge 전 최종 체크:**
- [ ] 모든 리뷰 코멘트에 응답했는가?
- [ ] "Request changes" 상태가 남아있지 않은가?
- [ ] 코드가 원래 목표를 달성했는가?

Merge 완료 후:
```bash
git checkout main
git pull origin main
```

- [ ] 리뷰를 모두 반영해서 Merge했다

---

### 시나리오 2 완료 체크

- [ ] 리뷰어를 지정하는 방법을 알게 되었다
- [ ] PR에 코멘트를 다는 방법을 알게 되었다
- [ ] 리뷰 후 코드를 수정하고 re-push 했다
- [ ] "PR에 re-push하면 자동으로 반영된다"는 것을 이해했다

## 시나리오 3 — AI 리뷰 통합

### 목표
PR 코드를 AI(ChatGPT, Claude 등)에 붙여넣어 리뷰 받는 방법을 익힌다.

### AI 리뷰가 필요한 이유

- 사람 리뷰어가 없을 때도 빠르게 피드백을 받을 수 있다
- 초보자가 놓치기 쉬운 패턴이나 오류를 미리 발견할 수 있다
- 코드 개선 방향을 제안받을 수 있다

**단, AI 리뷰의 한계:**
- AI가 항상 옳지는 않다
- 프로젝트 맥락을 완전히 이해하지 못할 수 있다
- AI 리뷰 후에도 사람 리뷰가 필요하다

---

### Step 3-1. PR 코드 복사하기

AI에게 리뷰 받을 코드를 준비합니다.

**방법 1 — GitHub 웹에서 diff 복사:**
1. PR 페이지 → "Files changed" 탭 클릭
2. 변경된 코드 전체를 드래그해서 복사
3. AI 대화창에 붙여넣기

**방법 2 — 터미널에서 diff 복사:**
```bash
# 현재 브랜치와 main의 차이 보기
git diff main..브랜치이름
```

```text
복사할 코드 (주요 부분 요약):
________________________________
________________________________
________________________________
```

- [ ] PR의 변경 코드를 준비했다

### Step 3-2. AI 리뷰 요청 프롬프트 만들기

AI에게 효과적으로 리뷰 받으려면 맥락을 충분히 제공해야 합니다.

**기본 리뷰 요청 프롬프트:**
```text
아래 코드는 GitHub PR에서 변경된 내용이야.
초보자가 작성한 코드를 리뷰해줘.

[변경 목적]
README에 프로젝트 설명 섹션을 추가했다.

[변경된 코드]
(코드 붙여넣기)

리뷰 요청 사항:
1. 내용이 초보자도 이해하기 쉬운가?
2. 빠진 부분이 있는가?
3. 개선할 점이 있다면 2~3가지만 알려줘.
```

**코드 품질 집중 리뷰 요청 프롬프트:**
```text
아래 Python 코드를 초보자 관점에서 리뷰해줘.

[코드]
(코드 붙여넣기)

확인해줘:
1. 코드에 버그나 오류가 있는가?
2. 더 읽기 쉽게 바꿀 수 있는 부분이 있는가?
3. 초보자가 이해하기 어려운 부분이 있는가?
답변은 짧게, 3가지 이내로 줘.
```

**나만의 리뷰 요청 프롬프트 만들기:**
```text
변경 목적:
________________________________

확인해달라고 할 내용 (3가지):
1. ________________________________
2. ________________________________
3. ________________________________
```

- [ ] AI 리뷰 요청 프롬프트를 만들었다

### Step 3-3. AI 리뷰 실행하기

1. ChatGPT, Claude, 또는 다른 AI 도구를 엽니다
2. 위에서 만든 프롬프트를 붙여넣고 코드도 함께 붙여넣습니다
3. AI의 답변을 받습니다

```text
AI가 제안한 수정사항:

1. ________________________________
   → 반영 여부: [ ] 반영  [ ] 나중에  [ ] 생략

2. ________________________________
   → 반영 여부: [ ] 반영  [ ] 나중에  [ ] 생략

3. ________________________________
   → 반영 여부: [ ] 반영  [ ] 나중에  [ ] 생략
```

- [ ] AI 리뷰를 받았다
- [ ] AI 피드백 중 반영할 것과 생략할 것을 구분했다

### Step 3-4. AI 리뷰 결과를 PR에 반영하기

AI 리뷰에서 반영할 내용이 있으면 코드를 수정하고 re-push 합니다.

```bash
# 코드 수정 후
git add ________________________________
git commit -m "refactor: AI 리뷰 반영 — ________________________________"
git push origin ________________________________
```

PR 코멘트에 AI 리뷰 결과를 간단히 남겨두면 좋습니다.

**PR 코멘트 예시:**
```text
AI 리뷰 결과를 반영했습니다.
- [수정한 내용 1]
- [수정한 내용 2]
```

- [ ] AI 리뷰 결과를 반영해서 re-push했다
- [ ] PR 코멘트에 AI 리뷰 결과를 기록했다

### Step 3-5. AI 리뷰 vs 사람 리뷰 비교

AI 리뷰와 사람 리뷰를 모두 받아봤다면, 비교해보세요.

```text
AI 리뷰가 잘 찾아낸 것:
________________________________

사람 리뷰가 더 잘 찾아낸 것:
________________________________

AI 리뷰에서 틀리거나 맞지 않았던 것:
________________________________
```

**AI 리뷰와 사람 리뷰의 차이를 정리하면:**

| 항목 | AI 리뷰 | 사람 리뷰 |
|------|---------|----------|
| 속도 | 빠름 | 상황에 따라 다름 |
| 코드 문법 오류 | 잘 찾음 | 놓칠 수 있음 |
| 비즈니스 맥락 이해 | 약함 | 강함 |
| 초보자 눈높이 | 프롬프트에 따라 다름 | 사람에 따라 다름 |
| 대화 가능 여부 | 가능 (바로 질문 가능) | 시간이 필요 |

## 자주 실수하는 것 5가지 + 해결법

### 실수 1 — main 브랜치에 직접 커밋하기

**상황:** `git checkout main` 상태에서 파일을 수정하고 커밋했다.

**왜 문제인가?**
- main 브랜치는 "완성된 코드"만 있어야 한다
- 리뷰 없이 main에 올라가면 팀 전체에 영향을 준다
- PR을 통한 검토 흐름이 무너진다

**해결법:**
```bash
# 실수로 main에 커밋한 경우
# 새 브랜치를 만들면 커밋이 거기에도 있음
git checkout -b feature/내-작업-브랜치

# main에서 마지막 커밋 되돌리기 (아직 push 전일 때만)
git checkout main
git reset --soft HEAD~1
```

**예방법:**
```bash
# 항상 작업 전에 현재 브랜치 확인
git branch --show-current
```

```text
이 실수를 방지하기 위해 기억할 것:
________________________________
```

### 실수 2 — 커밋 메시지를 너무 막연하게 쓰기

**나쁜 예:**
```
수정함
업데이트
작업
asdfgh
```

**왜 문제인가?**
- 나중에 어떤 변경인지 알 수 없다
- 팀원이 히스토리를 볼 때 이해가 안 된다
- PR 리뷰할 때 맥락을 파악하기 어렵다

**해결법:** 커밋 메시지 규칙 표를 참고해서 작성
```
feat: 메모 저장 기능 추가
fix: 삭제 버튼 오류 수정
docs: README 설치 방법 업데이트
```

**연습:**  
아래 막연한 커밋 메시지를 좋은 것으로 바꿔보세요.

```text
"수정함" → ________________________________
"업데이트" → ________________________________
"버그 고침" → ________________________________
```

---

### 실수 3 — 한 PR에 너무 많은 변경 넣기

**나쁜 예:**
- 파일 10개를 한 번에 수정
- 기능 추가 + 버그 수정 + 리팩토링을 한 PR에 합침

**왜 문제인가?**
- 리뷰하는 사람이 전체를 이해하기 어렵다
- 어느 변경이 어떤 문제를 일으켰는지 찾기 어렵다
- Merge 후 문제 생기면 되돌리기 어렵다

**해결법:** "PR 하나 = 하나의 목적"

```
좋은 PR 크기 기준:
- 파일 수: 5개 이내
- 변경 줄 수: 200줄 이내
- 목적: 딱 하나
```

---

### 실수 4 — push 전에 pull 안 하기

**상황:** 팀원이 main을 업데이트했는데, 나는 오래된 버전에서 작업했다.

**왜 문제인가?**
- push할 때 충돌이 생긴다
- merge conflict를 해결해야 한다

**해결법:**
```bash
# 항상 새 브랜치 만들기 전에
git checkout main
git pull origin main
# 그 다음 새 브랜치 생성
git checkout -b 새브랜치
```

**예방법:**
```text
새 작업을 시작하기 전에 항상 먼저 할 것:
1. git checkout main
2. git pull origin main
3. git checkout -b ________________________________
```

---

### 실수 5 — PR 설명 없이 올리기

**나쁜 PR:**
```
제목: 수정
설명: (없음)
```

**왜 문제인가?**
- 리뷰어가 무엇을, 왜 바꿨는지 알 수 없다
- 코드만 보고 의도를 파악해야 하는 부담이 생긴다

**해결법:** PR 설명 템플릿 항상 사용
```
## 변경 내용
(무엇을 바꿨는가)

## 이유
(왜 바꿨는가)

## 테스트 방법
(어떻게 확인했는가)

## 관련 Issue
Closes #번호
```
