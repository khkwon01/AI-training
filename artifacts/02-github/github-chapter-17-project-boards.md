# Chapter 17: Project Board와 Milestone

## 이 장에서 배우는 것

- GitHub Project Board(프로젝트 보드)가 무엇인지, 왜 쓰는지 이해한다
- 칸반(Kanban) 방식으로 할 일 카드를 만들고 이동하는 방법을 익힌다
- Milestone(마일스톤)을 만들어 이슈와 PR을 묶어서 관리하는 방법을 배운다
- 팀 혼자 또는 팀원과 함께 작업 진행 상황을 한눈에 파악하는 방법을 실습한다
- 프로젝트 보드와 마일스톤을 연동해서 릴리스 계획을 세우는 방법을 경험한다

---

## 먼저 쉬운 설명

코드를 혼자 짤 때는 머릿속에서 "오늘 이거 하고, 내일 저거 하면 되겠다"가 통합니다. 그런데 팀원이 생기거나, 작업이 열 개가 넘어가기 시작하면 상황이 달라집니다. "그 버그 누가 맡았더라?", "이번 주 배포에 어떤 기능이 들어가야 하지?" 같은 질문에 모두가 다른 답을 내놓기 시작합니다.

GitHub Project Board는 포스트잇을 붙이는 화이트보드와 같습니다. To Do(할 일) → In Progress(진행 중) → Done(완료) 열에 카드를 옮기면서 지금 팀이 무엇을 하고 있는지 한눈에 보여줍니다.

Milestone은 달력에 동그라미 치는 것과 같습니다. "v1.0 출시 — 6월 30일"이라는 목표를 만들고, 그 목표에 필요한 이슈들을 묶어두면 "우리가 출시까지 몇 %나 왔나"를 자동으로 계산해 줍니다.

이 두 가지를 함께 쓰면 코드보다 '흐름'을 관리하는 힘이 생깁니다. 협업 경험이 없어도 이 장을 마치면 실제 팀 프로젝트에서 바로 쓸 수 있습니다.

## 1. GitHub Project Board 기본 개념

Project Board는 세 가지 기본 열(column)로 구성됩니다.

| 열 이름 | 의미 | 카드가 여기 있을 때 |
|---|---|---|
| **To Do** | 아직 시작 안 함 | 이슈가 열려 있고 아무도 작업 중이 아님 |
| **In Progress** | 지금 누군가 하고 있음 | 담당자가 브랜치를 만들고 작업 중 |
| **Done** | 완료 | PR이 머지되었거나 이슈가 닫힘 |

카드 하나는 세 가지 중 하나입니다.

- **이슈(Issue)** — "로그인 버튼이 안 눌린다" 같은 할 일
- **PR(Pull Request)** — 코드 변경 제안
- **노트(Note)** — 이슈 없이 간단히 메모만 적은 카드

### 보드 만드는 위치 확인

```
GitHub 저장소 페이지
  └── 상단 탭: Code | Issues | Pull requests | Actions | Projects | ...
                                                                  ↑
                                                          여기를 클릭
```

### 자동화 설정 예시

보드를 만들 때 **"Automated kanban"** 템플릿을 고르면 아래 규칙이 자동 적용됩니다.

```
이슈 생성  →  자동으로 To Do 열에 카드 추가
PR 오픈    →  자동으로 In Progress 열로 이동
PR 머지    →  자동으로 Done 열로 이동
이슈 닫힘  →  자동으로 Done 열로 이동
```

수동으로 드래그해서 옮길 수도 있지만, 자동화를 쓰면 깜빡 잊고 안 옮기는 실수를 막을 수 있습니다.

## 2. 이슈를 보드 카드로 연결하기

이슈를 먼저 만들고, 그 이슈를 보드에 추가하는 흐름이 가장 안정적입니다.

### 이슈 제목 작성 패턴 (팀 권장)

```
[타입] 짧은 설명

예시:
[feat] 회원가입 이메일 인증 추가
[fix] 로그인 후 리다이렉트 경로 오류
[docs] README에 로컬 실행 방법 작성
[chore] GitHub Actions Python 버전 3.12로 업그레이드
```

### 이슈 본문 템플릿 (`.github/ISSUE_TEMPLATE/feature.md`)

```markdown
---
name: 기능 요청
about: 새 기능을 제안할 때 사용하세요
---

## 무엇을 하려고 하나요?
<!-- 기능을 한 문장으로 설명 -->

## 왜 필요한가요?
<!-- 이 기능이 없으면 어떤 불편이 있나요? -->

## 완료 기준
- [ ] 조건 1
- [ ] 조건 2

## 관련 마일스톤
<!-- 예: v1.0 출시 -->
```

이 파일을 저장소에 추가하면 이슈를 만들 때 자동으로 이 템플릿이 채워집니다.

### 이슈를 보드에 추가하는 방법

```
방법 A: 보드 화면에서
  → To Do 열 하단 "+ Add cards" 클릭
  → 이슈 번호 또는 제목으로 검색
  → 드래그해서 열에 배치

방법 B: 이슈 화면에서
  → 이슈 오른쪽 사이드바
  → "Projects" 항목 클릭
  → 연결할 보드 선택
```

## 3. Milestone(마일스톤) 만들고 관리하기

마일스톤은 **Issues 탭 → Milestones** 에서 만듭니다.

### 마일스톤 생성 정보

```
제목(Title):      v1.0 — 사용자 인증 기능 완성
설명(Description): 회원가입, 로그인, 로그아웃, 이메일 인증 포함
기한(Due date):   2026-06-30
```

### 이슈를 마일스톤에 연결하기

```
이슈 오른쪽 사이드바
  └── Milestone
        └── 드롭다운에서 "v1.0 — 사용자 인증 기능 완성" 선택
```

여러 이슈를 한 번에 연결할 때는 **Issues 탭 → 체크박스 선택 → Milestone 드롭다운** 을 사용합니다.

### 마일스톤 진행률 계산 방식

```
진행률(%) = 닫힌 이슈 수 / 전체 이슈 수 × 100

예시:
  전체 이슈: 8개
  닫힌 이슈: 5개
  진행률:   62%  ← GitHub이 자동으로 계산해서 표시
```

마일스톤 화면에서 이 막대 그래프를 보면 출시가 얼마나 남았는지 바로 파악할 수 있습니다.

## 4. 보드와 마일스톤을 함께 쓰는 흐름

실제 팀에서 가장 많이 쓰는 패턴입니다.

```
1. 마일스톤 생성
   "v1.0 출시" (기한: 6월 30일)

2. 이슈 생성 + 마일스톤 연결
   #12 [feat] 회원가입 폼 → v1.0
   #13 [feat] 로그인 API  → v1.0
   #14 [fix]  세션 만료 처리 → v1.0

3. 보드에 이슈 카드 배치
   To Do: #12, #13, #14

4. 작업 시작 → In Progress로 이동
   In Progress: #13 (김개발 담당)

5. PR 머지 → Done으로 자동 이동
   Done: #13

6. 마일스톤 진행률 확인
   v1.0: 1/3 완료 (33%)
```

### GitHub CLI로 마일스톤 정보 확인하기

```bash
# 마일스톤 목록 확인
gh api repos/{owner}/{repo}/milestones \
  --jq '.[] | "\(.title) — 진행률: \(.closed_issues)/\(.open_issues + .closed_issues)"'

# 특정 마일스톤에 연결된 이슈 목록
gh issue list --milestone "v1.0 출시"
```

```
출력 예시:
#14  open   세션 만료 처리     about 2 days ago
#12  open   회원가입 폼        about 3 days ago
```

## 5. Projects (new) — GitHub의 최신 보드 시스템

2022년 이후 GitHub은 **Projects (beta → GA)** 라는 새 버전을 기본으로 제공합니다. 기존 Classic Project Board보다 강력합니다.

### 차이점 한눈에 보기

| 항목 | Classic Board | Projects (new) |
|---|---|---|
| 뷰 종류 | 칸반만 가능 | 칸반 + 테이블 + 로드맵 |
| 커스텀 필드 | 불가 | 날짜, 숫자, 선택지 등 추가 가능 |
| 여러 저장소 연결 | 불가 | 가능 (조직 레벨) |
| 자동화 | 제한적 | 워크플로우 에디터 제공 |

### 커스텀 필드 예시

```
프로젝트 설정 → + Add field

필드 이름: 우선순위
필드 타입: Single select
옵션:
  🔴 긴급
  🟡 보통
  🟢 낮음
```

이렇게 만든 필드는 테이블 뷰에서 이슈마다 직접 선택할 수 있습니다.

### 로드맵 뷰 설정

```
+ New view → Roadmap

날짜 필드:
  시작일: Start date (커스텀 필드)
  종료일: Due date (마일스톤 기한 또는 커스텀 필드)

이렇게 설정하면 간트 차트처럼 시각화됩니다.
```

## 따라 하기 실습

### 실습 1 — 마일스톤과 이슈 만들기

**목표**: "v0.1 — 초기 설정 완료"라는 마일스톤을 만들고, 이슈 3개를 연결합니다.

1. 저장소 **Issues** 탭 → **Milestones** → **New milestone** 클릭
2. 아래 내용으로 마일스톤을 만듭니다.
   ```
   제목:  v0.1 — 초기 설정 완료
   기한:  오늘 날짜 + 7일
   설명:  프로젝트 뼈대 구성 완료
   ```
3. **Issues** 탭 → **New issue** 를 눌러 이슈 3개를 만듭니다.
   ```
   이슈 1: [chore] .gitignore 파일 추가
   이슈 2: [docs] README 초안 작성
   이슈 3: [chore] GitHub Actions 기본 워크플로우 추가
   ```
4. 각 이슈의 오른쪽 사이드바 **Milestone** 에서 `v0.1 — 초기 설정 완료` 를 선택합니다.
5. Milestones 목록으로 돌아와서 진행률이 **0%** 로 표시되는지 확인합니다.

---

### 실습 2 — 프로젝트 보드 만들고 카드 배치하기

**목표**: 실습 1에서 만든 이슈들을 보드에서 관리합니다.

1. 저장소 **Projects** 탭 → **New project** → **Board** 템플릿 선택
2. 프로젝트 이름을 `초기 설정 보드` 로 입력하고 생성합니다.
3. **To Do** 열 하단 **+ Add item** 클릭 → `#` 을 입력해서 실습 1에서 만든 이슈 3개를 추가합니다.
4. 이슈 1(`[chore] .gitignore 파일 추가`)을 클릭해서 **In Progress** 열로 드래그합니다.
5. GitHub에서 직접 `.gitignore` 파일을 만들고 이슈를 닫습니다(Close issue).
6. 보드에서 해당 카드가 **Done** 열로 이동했는지 확인합니다.
7. Milestones 화면으로 돌아가 진행률이 **33%** 가 되었는지 확인합니다.

---

### 실습 3 — CLI로 이슈 상태 한 번에 확인하기

**목표**: 터미널에서 마일스톤 진행 현황을 조회합니다.

1. 터미널을 열고 저장소 폴더로 이동합니다.
   ```bash
   cd my-project
   ```
2. GitHub CLI가 설치되어 있는지 확인합니다.
   ```bash
   gh --version
   # 출력 예시: gh version 2.49.0 (2024-05-01)
   ```
3. 마일스톤에 연결된 열린 이슈 목록을 조회합니다.
   ```bash
   gh issue list --milestone "v0.1 — 초기 설정 완료" --state open
   ```
   ```
   출력 예시:
   #3  open  GitHub Actions 기본 워크플로우 추가  about 1 hour ago
   #2  open  README 초안 작성                    about 1 hour ago
   ```
4. 이슈 2를 커맨드라인으로 닫아봅니다.
   ```bash
   gh issue close 2 --comment "README 초안 작성 완료"
   ```
5. 다시 목록을 조회해서 이슈 2가 사라졌는지 확인합니다.

## 자주 하는 실수

| 실수 | 오류 메시지 또는 증상 | 해결 방법 |
|---|---|---|
| 마일스톤을 이슈에 연결 안 함 | 마일스톤 진행률이 0%에서 안 바뀜 | 이슈 오른쪽 사이드바 → Milestone에서 직접 선택 |
| PR을 머지해도 보드 카드가 안 움직임 | Done 열이 비어 있음 | Classic Board는 PR이 아닌 이슈를 닫아야 자동 이동. 또는 Automated kanban 설정 재확인 |
| `gh issue list --milestone` 이 결과를 안 보여줌 | `no issues match your search` | 마일스톤 이름의 띄어쓰기와 대소문자를 정확히 일치시켜야 함 |
| 보드에 카드가 중복으로 생김 | 같은 이슈가 두 열에 표시 | 한 이슈는 한 보드에서 하나의 열에만 존재함. 수동 추가 시 이미 추가된 이슈를 다시 추가하면 중복처럼 보이지만 실제로는 같은 카드 |
| 기한(Due date)이 지난 마일스톤 색이 빨간색으로 변함 | 빨간 날짜 표시 | 기한을 연장하거나, 완료된 이슈를 전부 닫아서 마일스톤을 close 처리 |
| Projects (new) 와 Classic Board를 혼동 | 자동화 설정 화면이 다르게 생김 | 저장소 설정 → Features에서 어느 버전인지 확인. 새 저장소는 Projects (new)가 기본 |
| 이슈를 닫지 않고 PR만 머지함 | 마일스톤 진행률이 안 올라감 | PR 본문에 `Closes #이슈번호` 를 추가하면 머지 시 이슈가 자동으로 닫힘 |

## 확인 체크리스트

- [ ] 마일스톤을 하나 이상 만들었고, 제목과 기한이 설정되어 있다
- [ ] 이슈 3개 이상이 마일스톤에 연결되어 있다
- [ ] 마일스톤 진행률이 이슈를 닫을 때마다 자동으로 올라간다
- [ ] 프로젝트 보드에 To Do, In Progress, Done 세 열이 있다
- [ ] 이슈 카드를 드래그해서 열 사이를 이동할 수 있다
- [ ] PR 본문에 `Closes #번호` 를 쓰면 머지 시 이슈가 자동으로 닫힌다는 것을 이해한다
- [ ] `gh issue list --milestone "마일스톤이름"` 으로 이슈 목록을 조회할 수 있다
- [ ] Classic Board와 Projects (new)의 차이점을 말할 수 있다

## 한 번 더 생각해 보기

1. **마일스톤 하나에 이슈를 몇 개까지 넣는 게 적절할까요?** 이슈가 너무 많으면 어떤 문제가 생기고, 너무 적으면 어떤 정보를 놓치게 될까요? 실제 1주일 스프린트를 기준으로 생각해 보세요.

2. **"보드에서 In Progress 열에 카드가 10개 쌓여 있다"는 상황은 무엇을 의미할까요?** 팀이 열심히 일하고 있다는 신호일까요, 아니면 뭔가 막혀 있다는 경고 신호일까요? 어떻게 대응하면 좋을지 생각해 보세요.

3. **PR 본문에 `Closes #12` 를 쓰는 것과 이슈를 수동으로 닫는 것의 차이는 무엇일까요?** 코드 리뷰어가 PR을 볼 때 어느 방법이 더 많은 정보를 주는지 생각해 보세요.
