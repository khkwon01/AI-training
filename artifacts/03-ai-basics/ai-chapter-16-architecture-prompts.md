## 이 장에서 배우는 것

- 소프트웨어 아키텍처 설계에 AI를 활용하는 프롬프트 패턴 5가지
- 좋은 프롬프트와 나쁜 프롬프트의 차이를 직접 비교하는 방법
- 역할(Role), 맥락(Context), 제약(Constraint) 세 요소로 프롬프트를 구조화하는 방법
- API 설계, DB 스키마, 시스템 분리(마이크로서비스) 같은 실전 주제에 프롬프트 패턴을 적용하는 방법
- AI가 낸 결과물을 검토하고 반복적으로 개선하는 워크플로우

---

## 먼저 쉬운 설명

건축가가 건물을 지을 때 "집 하나 지어 주세요"라고 하지 않습니다. 층수, 용도, 예산, 법적 제약을 모두 말하죠. 소프트웨어 아키텍처 설계도 똑같습니다.

AI에게 "쇼핑몰 만들어 줘"라고 하면 너무 막연합니다. 하지만 "월 100만 명이 사용하는 한국어 쇼핑몰의 주문 서비스를 설계해 줘. 재고 서비스와 결제 서비스는 이미 있고, 메시지 큐는 AWS SQS를 써야 해"라고 하면 AI는 훨씬 구체적이고 쓸 수 있는 답을 내놓습니다.

이 장에서는 **프롬프트 패턴(Prompt Pattern)**이라는 틀을 배웁니다. 패턴은 반복해서 쓸 수 있는 틀입니다. 한 번 익히면 어떤 아키텍처 문제에도 빠르게 적용할 수 있습니다.

## 1. Role-Context-Constraint 패턴 (역할-맥락-제약)

가장 기본이 되는 패턴입니다. 프롬프트를 세 부분으로 나눕니다.

| 요소 | 설명 | 예시 |
|------|------|------|
| **Role (역할)** | AI에게 어떤 전문가처럼 답하라고 지시 | "시니어 백엔드 아키텍트로서" |
| **Context (맥락)** | 현재 상황, 기술 스택, 팀 규모 | "FastAPI + PostgreSQL, 팀원 3명" |
| **Constraint (제약)** | 반드시 지켜야 할 조건 | "AWS 프리 티어 안에서, 배포는 Docker로" |

**나쁜 프롬프트 예시:**

```
사용자 인증 시스템 설계해 줘.
```

**좋은 프롬프트 예시 (RCC 패턴 적용):**

```
[Role] 시니어 백엔드 아키텍트로서 조언해 줘.

[Context]
- 서비스: 소규모 B2B SaaS (월 활성 사용자 5,000명)
- 기술 스택: FastAPI, PostgreSQL, Redis
- 현재 상태: 인증 기능이 없는 MVP 단계

[Constraint]
- JWT + Refresh Token 방식 사용
- 소셜 로그인(구글)은 나중에 추가할 수 있어야 함
- 응답은 Python 코드 포함, 파일 구조도 보여 줘

사용자 인증 시스템을 설계해 줘.
```

**실습 파일: `prompts/01_rcc_auth.txt`**

```text
# RCC 패턴 템플릿

[Role]
{전문가 역할}로서 조언해 줘.

[Context]
- 서비스: {서비스 설명}
- 기술 스택: {사용 기술}
- 현재 상태: {현재 단계}

[Constraint]
- {제약 조건 1}
- {제약 조건 2}
- {출력 형식 요구}

{실제 질문}
```

## 2. Step-by-Step 분해 패턴 (단계별 분해)

복잡한 아키텍처 문제는 한 번에 물으면 AI도 헷갈립니다. 큰 문제를 작게 쪼개서 단계별로 묻는 패턴입니다.

**잘못된 방식 — 한 번에 너무 많이 묻기:**

```
마이크로서비스 아키텍처로 전환하는 방법,
각 서비스의 DB 설계, API 게이트웨이 설정,
서비스 간 통신 방법을 모두 알려 줘.
```

**올바른 방식 — 단계별로 나누기:**

```python
# step1_decompose_prompt.py
# AI와 대화할 때 사용하는 프롬프트 시퀀스를 코드처럼 설계합니다.

prompts = {
    "step_1_domain": """
        우리 서비스의 도메인을 분석해 줘.
        아래 기능 목록을 보고 어떤 마이크로서비스로
        나눌 수 있는지 후보를 제안해 줘. 이유도 설명해 줘.

        기능 목록:
        - 회원 가입 / 로그인
        - 상품 등록 / 조회
        - 주문 생성 / 취소
        - 결제 처리
        - 알림 발송 (이메일, SMS)
    """,

    "step_2_dependency": """
        위에서 나온 서비스 목록을 기준으로,
        각 서비스 간 의존 관계를 화살표로 표현해 줘.
        순환 의존(A → B → A)이 있으면 어떻게 해결할지도 설명해 줘.
    """,

    "step_3_db": """
        {서비스 이름} 서비스의 데이터베이스 스키마를 설계해 줘.
        다른 서비스의 데이터를 직접 조회하지 않도록
        서비스 경계를 지켜서 설계해 줘.
        PostgreSQL DDL로 작성해 줘.
    """,
}
```

> **핵심 원칙:** 이전 단계의 AI 답변을 다음 프롬프트에 붙여 넣어 맥락을 이어 가세요. AI는 이전 대화를 기억하지만, 명시적으로 넣어 주면 더 정확해집니다.

## 3. Persona 비교 패턴 (전문가 관점 비교)

같은 설계 문제를 서로 다른 관점에서 검토하고 싶을 때 씁니다. 토론하듯 여러 전문가의 의견을 한 번에 받을 수 있습니다.

**프롬프트 예시:**

```python
# prompts/03_persona_compare.py

persona_prompt = """
아래 API 설계안을 세 가지 관점에서 검토해 줘.

## 검토할 설계안
POST /orders
{
  "user_id": 123,
  "items": [{"product_id": 1, "qty": 2}],
  "coupon_code": "SAVE10"
}

## 관점 1: 보안 전문가
- 입력 유효성 검사에서 놓친 부분은?
- 인증/인가 관련 문제는?

## 관점 2: 성능 엔지니어
- 이 API가 초당 1,000 요청을 받을 때 병목은?
- DB 쿼리 최적화 포인트는?

## 관점 3: 주니어 개발자
- 이 API를 처음 쓰는 사람이 헷갈릴 부분은?
- 에러 메시지는 충분히 친절한가?

각 관점에서 문제점과 개선안을 bullet point로 정리해 줘.
"""
```

    """

        "성능": [],

## 4. Template 채우기 패턴 (빈칸 채우기)

반복되는 설계 작업(예: 새 API 엔드포인트마다 문서 작성)을 자동화할 때 씁니다. AI에게 템플릿을 주고 채워 달라고 합니다.

**`templates/api_design_template.md`:**

```markdown
# API 설계 문서: {엔드포인트 이름}

## 기본 정보
- Method: {GET | POST | PUT | DELETE}
- Path: {경로}
- 인증 필요: {Yes | No}

## 요청
### Headers
| 헤더 | 필수 | 설명 |
|------|------|------|
| Authorization | Yes | Bearer {token} |

### Body
```json
{
  // 필드명: 타입, 설명, 필수 여부
}
```

## 응답
### 성공 (200 OK)
```json
{
  // 응답 예시
}
```

### 실패 케이스
| HTTP 코드 | 에러 코드 | 설명 |
|-----------|-----------|------|
| 400 | INVALID_INPUT | 입력 유효성 오류 |
| 401 | UNAUTHORIZED | 인증 실패 |

## 비즈니스 규칙
- {규칙 1}
- {규칙 2}
```

**AI에게 보내는 프롬프트:**

```
위 템플릿을 사용해서 아래 기능의 API를 설계해 줘.

기능: 사용자가 장바구니에 상품을 추가한다.
조건:
- 같은 상품을 두 번 추가하면 수량이 합산된다.
- 재고가 부족하면 추가할 수 없다.
- 비로그인 사용자도 임시 장바구니를 쓸 수 있다 (세션 기반).

템플릿의 모든 섹션을 빠짐없이 채워 줘.
```

## 5. 반복 개선 패턴 (Iterative Refinement)

첫 번째 AI 답변은 항상 완벽하지 않습니다. "아니, 더 좋게"가 아니라 **구체적인 기준으로 개선**을 요청하는 패턴입니다.

**`scripts/iterative_prompt.py`:**

```python
# AI와 반복 대화를 구조화하는 예시

INITIAL_PROMPT = """
간단한 URL 단축 서비스의 시스템 아키텍처를 설계해 줘.
다이어그램은 텍스트 형식(ASCII)으로 그려 줘.
"""

REFINEMENT_PROMPTS = [
    # 1차 개선: 스케일 추가
    """
    위 설계에서 하루 100만 건의 단축 URL 생성 요청을 처리해야 한다면
    어떤 부분을 바꿔야 해? 변경된 부분만 설명해 줘.
    """,

    # 2차 개선: 장애 대응 추가
    """
    Redis가 갑자기 다운됐을 때 서비스가 어떻게 동작해야 해?
    Fallback 전략을 아키텍처에 추가해 줘.
    """,

    # 3차 개선: 비용 최적화
    """
    현재 설계를 AWS 기준으로 월 비용 예측을 해 줘.
    같은 성능을 유지하면서 비용을 줄일 수 있는 방법이 있어?
    """,
]

def print_session_guide():
    print("=== 반복 개선 세션 가이드 ===")
    print(f"[초기 프롬프트]\n{INITIAL_PROMPT}")
    for i, prompt in enumerate(REFINEMENT_PROMPTS, 1):
        print(f"\n[{i}차 개선 프롬프트]\n{prompt}")
```

> **팁:** 각 개선 요청 앞에 "위 설계를 유지하면서"라고 붙이면 AI가 처음부터 다시 설계하지 않고 기존 맥락을 이어 갑니다.

## 자주 하는 실수

| 실수 | 증상 / 에러 메시지 | 원인 | 해결 방법 |
|------|-------------------|------|-----------|
| 너무 짧은 프롬프트 | AI가 "더 자세히 알려주세요"라고 되묻거나 너무 일반적인 답을 줌 | 맥락 부족 | RCC 패턴으로 Role, Context, Constraint를 모두 포함시킴 |
| 여러 질문을 한 번에 | 답변이 길고 산만하며 핵심이 없음 | 질문 과부하 | Step-by-Step 패턴으로 질문을 3개 이하로 분리 |
| AI 결과를 그대로 사용 | 실제 코드에 적용 시 `ImportError`, `AttributeError` 발생 | AI가 라이브러리 버전을 모름 | 프롬프트에 `requirements.txt` 내용 포함, 결과는 반드시 테스트 |
| 개선 요청이 모호함 | "더 좋게 해 줘" → AI가 구조 전체를 바꿔 버림 | 기준 불명확 | "X 부분만, Y 조건을 추가해서, 나머지는 유지해 줘" 형식으로 요청 |
| 맥락 없이 이어 묻기 | AI가 이전과 다른 기술 스택을 사용하거나 설계를 처음부터 다시 함 | 대화 맥락 손실 | 새 대화를 시작할 때 이전 설계안을 프롬프트에 다시 붙여 넣음 |
| 출력 형식 미지정 | 코드와 설명이 뒤섞여 파싱이 어려움 | 형식 지시 누락 | "코드는 Python 코드 블록으로, 설명은 bullet point로" 명시 |

## 확인 체크리스트

- [ ] RCC 패턴의 세 요소(Role, Context, Constraint)를 설명할 수 있다
- [ ] 나쁜 프롬프트와 좋은 프롬프트의 차이를 예시로 들 수 있다
