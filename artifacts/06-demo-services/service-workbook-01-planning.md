# Service Planning Workbook 01
## 서비스 기획 — 5단계 프로세스 실습

> 이 워크북은 직접 빈칸을 채우고 예시를 따라 하며 서비스를 기획하는 형식입니다.  
> 코딩보다 먼저 "무엇을, 누구를 위해, 어떻게 만들지"를 정리합니다.

---

## 이 워크북이 필요한 이유

초보자가 서비스를 만들 때 가장 많이 실패하는 이유:

1. 무엇을 만들지 정하지 않고 코딩을 시작한다
2. 처음부터 너무 큰 기능을 목표로 삼는다
3. 데이터를 어떻게 저장할지 생각하지 않는다
4. API가 무엇인지 모르고 만들기 시작한다

이 워크북은 코딩을 시작하기 전에 이 4가지를 정리하는 연습입니다.

---

## 시작 전 체크

- [ ] 노트와 펜(또는 메모 앱)을 준비했다
- [ ] 만들고 싶은 서비스 아이디어가 어렴풋이 있다
- [ ] 완벽한 기획이 아니어도 괜찮다는 것을 안다

---

## 완성된 기획서 예시 (메모 서비스)

단계를 시작하기 전에, 완성된 모습을 먼저 확인해보세요.  
이 예시를 참고해서 각 단계의 빈칸을 채워 나가면 됩니다.

```
=== 메모 서비스 기획서 ===

서비스 이름: 나의 메모장
한 줄 설명: 간단한 메모를 저장하고 확인할 수 있는 웹 서비스
사용자: 할 일과 메모를 기록하고 싶은 초등학생~중학생
해결하는 문제: 중요한 것을 적어두고 나중에 확인하지 못하는 문제

핵심 기능 3가지:
  1. 메모 추가하기 (글자 입력 → 저장 버튼)
  2. 메모 목록 보기 (저장된 메모 전체 표시)
  3. 메모 삭제하기 (더 필요 없는 메모 지우기)

데이터 구조 (JSON):
  {
    "id": 1,
    "content": "수학 숙제 3페이지 풀기",
    "created_at": "2025-06-01"
  }

API 엔드포인트:
  GET  /memos       → 전체 메모 목록 조회
  POST /memos       → 새 메모 추가
  DELETE /memos/:id → 특정 메모 삭제
```

## 단계 1 — 서비스 아이디어 정하기

### 왜 아이디어부터인가?

아이디어가 막연하면 기능을 정할 수 없고, 기능이 없으면 코딩을 시작할 수 없습니다.  
아이디어를 딱 3가지 질문으로 정리해 봅시다.

### 1-1. 세 가지 핵심 질문에 답하기

**질문 1: 무엇을 만들까?**

좋은 서비스 아이디어는 "___를 할 수 있는 앱/사이트/서비스"로 표현됩니다.

| 예시 | 설명 |
|------|------|
| 메모 서비스 | 짧은 메모를 저장하고 볼 수 있는 앱 |
| 할 일 관리 | 오늘 할 일을 적고 완료 표시를 할 수 있는 앱 |
| 단어장 서비스 | 영어 단어와 뜻을 저장하고 복습하는 앱 |
| 독서 기록 | 읽은 책 제목과 감상을 기록하는 앱 |

```text
내가 만들 서비스는:

________________________________ 할 수 있는 서비스
```

**질문 2: 누가 쓸까?**

사용자를 구체적으로 정하면 기능을 어떻게 만들지 결정하기 쉬워집니다.

좋은 예시:
- "스마트폰을 자주 쓰는 중학생"
- "영어 공부를 시작하는 성인"
- "간단한 메모를 원하는 직장인"

너무 막연한 예시:
- "모든 사람" (누구를 위한 기능인지 알 수 없음)
- "사용자" (당연한 말이라 의미 없음)

```text
이 서비스를 쓸 사람:

나이/직업: ________________________________
어떤 상황에서 쓰는가: ________________________________
스마트폰/컴퓨터 중 주로 사용하는 것: ________________________________
```

**질문 3: 무슨 문제를 해결할까?**

좋은 서비스는 "이 문제 때문에 불편했는데, 이 서비스로 해결된다"라고 말할 수 있습니다.

예시:
```text
문제: 중요한 것을 떠올랐을 때 적어둘 곳이 없어서 나중에 잊어버린다.
해결: 언제 어디서나 바로 메모를 저장하고 꺼내볼 수 있게 한다.
```

```text
내 서비스가 해결하는 문제:

문제: ________________________________
      ________________________________

해결: ________________________________
      ________________________________
```

### 1-2. 서비스 한 줄 설명 완성하기

위의 세 가지 답을 합쳐서 한 문장으로 정리해보세요.

**형식:** `[사용자]가 [문제]를 해결하기 위해 [기능]을 쓸 수 있는 서비스`

예시:
```text

언제든 메모를 저장하고 확인할 수 있는 서비스
```

```text
내 서비스 한 줄 설명:

________________________________
________________________________
```

## 단계 2 — 핵심 기능 3개만 고르기

### 왜 3개인가?

처음부터 10가지 기능을 만들려 하면:
- 완성까지 너무 오래 걸린다
- 중간에 포기하기 쉽다
- 어떤 기능이 중요한지 모르게 된다

**핵심 기능 3개만 만들고 동작하면, 나머지는 나중에 추가합니다.**

### 2-1. 기능 후보 목록 만들기

내 서비스에 있으면 좋겠다고 생각하는 기능을 모두 적어보세요.

```text
기능 후보 목록 (생각나는 것 모두 적기):

1. ________________________________
2. ________________________________
3. ________________________________
4. ________________________________
5. ________________________________
6. ________________________________
7. ________________________________
(더 있으면 계속 적기)
```

### 2-2. 우선순위 결정 방법

각 기능 후보에 아래 세 가지 질문으로 점수를 매겨보세요.

| 질문 | Yes = 1점 | No = 0점 |
|------|-----------|----------|
| 이 기능 없으면 서비스가 동작하지 않는가? | 1 | 0 |
| 사용자가 매일 쓸 기능인가? | 1 | 0 |
| 만드는 데 오래 걸리지 않는가? | 1 | 0 |

**3점 = 핵심 기능 / 2점 = 중요 기능 / 1점 이하 = 나중에 추가**

점수 계산 연습:

```text
기능 이름: ________________________________
- 없으면 동작 안 함? [ ] Yes  [ ] No
- 매일 쓰는 기능?    [ ] Yes  [ ] No
- 만들기 쉬운가?     [ ] Yes  [ ] No
합계: ___ 점
```

### 2-3. 핵심 기능 3개 확정

점수가 높은 것 3가지를 골라보세요.

```text
핵심 기능 1: ________________________________
핵심 기능 2: ________________________________
핵심 기능 3: ________________________________
```

**메모 서비스 예시:**
```text
핵심 기능 1: 메모 추가하기 — 글자 입력 후 저장 버튼 클릭
핵심 기능 2: 메모 목록 보기 — 저장된 모든 메모 표시
핵심 기능 3: 메모 삭제하기 — 필요 없는 메모 제거
```

**지금 당장 필요 없는 기능 예시 (나중에 추가):**
- 로그인 / 회원가입
- 메모 검색
- 메모 수정
- 알림 기능
- 다른 사람과 공유

### 2-4. "나중에 추가" 목록 만들기

지금은 만들지 않지만 나중에 추가하고 싶은 기능을 적어두세요.


## 단계 3 — 데이터 구조 설계

### 데이터 구조란?

서비스가 저장하고 사용하는 정보의 형태를 말합니다.  
예를 들어 메모 서비스라면 각 메모에 어떤 정보가 필요한지를 정합니다.

### 3-1. 저장할 데이터 정하기

핵심 기능 3개를 동작시키기 위해 어떤 정보가 필요한지 생각해보세요.

**메모 서비스 예시:**
- 메모를 추가하려면 → "메모 내용"이 필요
- 목록을 보려면 → "저장된 모든 메모 내용"이 필요
- 삭제하려면 → "각 메모를 구별하는 번호(ID)"가 필요
- 언제 만들었는지 알려면 → "날짜"가 필요

```text
내 서비스에서 저장할 정보:

1. ________________________________ (이유: ________________________________)
2. ________________________________ (이유: ________________________________)
3. ________________________________ (이유: ________________________________)
4. ________________________________ (이유: ________________________________)
```

### 3-2. JSON 형식으로 표현하기

JSON은 데이터를 저장하고 전달하는 방법 중 하나입니다.  
아래처럼 `키: 값` 형식으로 씁니다.

**메모 서비스 데이터 예시:**
```json
{
  "id": 1,
  "content": "수학 숙제 3페이지 풀기",
  "created_at": "2025-06-01"
}
```

각 부분의 의미:
- `"id": 1` → 이 메모의 고유 번호 (각 메모를 구별하는 데 사용)
- `"content": "..."` → 메모 내용 (실제 저장하고 싶은 글자)
- `"created_at": "..."` → 만든 날짜 (언제 만들었는지 기록)

**전체 메모 목록은 이렇게 생겼습니다:**
```json
[
  {
    "id": 1,
    "content": "수학 숙제 3페이지 풀기",
    "created_at": "2025-06-01"
  },
  {
    "id": 2,
    "content": "엄마 생일 선물 사기",
    "created_at": "2025-06-02"
  }
]
```

### 3-3. 내 서비스 데이터 구조 설계하기

위 메모 예시를 참고해서 내 서비스의 데이터 구조를 JSON으로 써보세요.

```text
내 서비스의 데이터 구조 (JSON 형식):

{
  "id": _____,
  "________________": "________________",
  "________________": "________________",
  "________________": "________________"
}
```

예를 들어 단어장 서비스라면:
```json
{
  "id": 1,
  "word": "apple",
  "meaning": "사과",
  "example": "I eat an apple every day."
}
```

## 단계 4 — API 엔드포인트 설계

### API 엔드포인트란?

API는 서비스가 기능을 제공하는 "창구"입니다.  
엔드포인트는 그 창구의 "주소"입니다.

비유로 이해하기:
- **API** = 음식점
- **엔드포인트** = 메뉴판 (어떤 것을 주문할 수 있는지)
- **HTTP 메서드** = 주문 방식 (주문/취소/변경)

### 4-1. HTTP 메서드 기초

| 메서드 | 하는 일 | 비유 |
|--------|---------|------|
| GET | 데이터 가져오기 | 메뉴 보기 |
| POST | 새 데이터 추가하기 | 새 메뉴 주문하기 |
| DELETE | 데이터 삭제하기 | 주문 취소하기 |
| PUT/PATCH | 데이터 수정하기 | 주문 변경하기 |

### 4-2. 메모 서비스 API 엔드포인트 예시

```
메모 목록 조회:
  메서드: GET
  주소:   /memos
  설명:   저장된 메모 전체를 가져온다
  응답:   메모 목록 (JSON 배열)

새 메모 추가:
  메서드: POST
  주소:   /memos
  설명:   새로운 메모를 저장한다
  전달:   { "content": "새 메모 내용" }
  응답:   저장된 메모 (id 포함)

특정 메모 삭제:
  메서드: DELETE
  주소:   /memos/:id
  설명:   id에 해당하는 메모를 삭제한다
  예시:   /memos/1  → 1번 메모 삭제
  응답:   삭제 성공 여부
```

### 4-3. 엔드포인트 설계 규칙

좋은 엔드포인트 주소 만들기:

| 규칙 | 좋은 예 | 나쁜 예 |
|------|---------|---------|
| 복수형 명사 사용 | `/memos` | `/memo`, `/getMemos` |
| 동사 사용 금지 | `/memos` | `/createMemo` |
| 소문자 사용 | `/user-profiles` | `/UserProfiles` |
| ID는 경로에 포함 | `/memos/1` | `/memos?id=1` |

## 단계 5 — AI에게 기획 검토 요청하기

### 왜 AI에게 검토를 받는가?

혼자 기획하면 놓치기 쉬운 것들:
- 데이터 구조에서 필요한 필드가 빠졌는지
- API 설계에서 기능과 엔드포인트가 맞는지
- 기능이 실제로 동작 가능한지

AI에게 검토를 받으면 빠르게 문제를 발견할 수 있습니다.

### 5-1. AI 검토 요청 프롬프트 예시

**전체 기획 검토 요청:**
```text
초보자가 처음 만드는 간단한 웹 서비스 기획서야.
검토해줘.

서비스 이름: 나의 메모장
대상 사용자: 메모를 자주 잊어버리는 중학생
핵심 기능:
  1. 메모 추가
  2. 메모 목록 조회
  3. 메모 삭제

데이터 구조 (JSON):
{
  "id": 1,
  "content": "메모 내용",
  "created_at": "2025-06-01"
}

API 엔드포인트:
  GET    /memos
  POST   /memos
  DELETE /memos/:id

확인해줘:
1. 데이터 구조에 빠진 것이 있는가?
2. API 엔드포인트가 기능에 맞는가?
3. 초보자가 만들기에 너무 어렵지 않은가?
4. 개선할 점이 있다면 3가지 이내로 알려줘.
```
