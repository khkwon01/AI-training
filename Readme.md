# AI-training Harness

This repository is structured as a self-driving production harness for beginner-friendly coding education materials.

The target operating model is:

1. Research external programming, AI, GitHub, and AWS trends.
2. Decide which ideas are actually useful for beginner education.
3. Turn those findings into easy lessons, examples, exercises, and checklists.
4. Validate the lessons through small implementation and deployment exercises.
5. Produce a daily review before the next day continues.

The harness itself is not the product.

The product is:

- beginner-friendly lesson documents
- easy concept explanations
- clear tables of contents
- step-by-step follow-along exercises
- practice tasks and review checklists
- example code and deployment notes that can be used like a workbook or book chapter

## Source Review Loop

Educational content should be reviewed continuously against:

- user-provided materials and URLs
- official documentation
- reliable external learning resources
- research findings that change teaching priorities

The goal is not to copy sources into the curriculum. The goal is to detect:

- missing beginner concepts
- concepts that are too advanced too early
- weak explanations
- outdated examples
- places where a simpler example would teach better

## Best Practice

The best operating model for this repository is:

- Codex session as the real orchestrator
- local scripts for queue selection, bookkeeping, and state management
- daily review for quality control

In other words:

- `launchd` and `tick` help with repeatability
- Codex is still the main engine for judgment, synthesis, and content quality
- learner-facing content should not depend on blind background automation alone

## Repository Layout

- `harness/`: project-wide operating rules and defaults
- `missions/`: active and completed mission folders
- `scripts/`: bootstrap, status, and validation helpers
- `artifacts/`: durable outputs generated by missions
- `sources/`: registries and review logs for user-provided and external materials
- `tracks/`: lane and track definitions with backlogs

## Mission Contract

Each mission folder contains:

- `brief.md`: objective, acceptance criteria, constraints, references
- `plan.md`: concrete execution plan and checklist
- `journal.md`: timestamped work log
- `handoff.md`: summary for the next AI or human
- `state.json`: machine-readable status
- `artifacts/`: mission-specific outputs

This keeps the repo usable by both:

- an AI agent that needs deterministic files to read and update
- a human reviewer who wants to inspect progress quickly

## Content Standard

All learner-facing outputs should read like beginner teaching material.

Each educational artifact should usually contain:

- what the learner will learn
- easy concept explanation
- key terms
- step-by-step practice
- common mistakes
- a review checklist or short questions

The learner should not need to understand the internal harness to use the materials.

## Program Tracks

- `research`: external research for curriculum optimization
- `python`: Python education content and exercises
- `github`: GitHub education content and working practices
- `ai`: AI model usage, prompting, and AI-assisted coding content
- `development`: small validation builds to test whether the curriculum works
- `aws`: deployment and operations content plus validation exercises
- `daily-review`: daily summary, review, and next-day planning

## Operating Rules

1. Every mission must fit in about one hour.
2. Every mission belongs to one `track` and one `lane`.
3. Artifact file naming follows folder-prefixed conventions (e.g. `python-chapter-01.md`, `github-chapter-01.md`).
4. Shell environment variables use `AI_TRAIN_` because hyphens are not valid there.
5. Research findings must be reflected back into curriculum and content tracks continuously.
6. Every day ends with a review mission before the next day starts.
7. Learner-facing outputs must prioritize easy explanation over internal process detail.
8. When choosing between internal elegance and clearer teaching material, favor clearer teaching material.

## Default Daily Loop

1. Pick or create missions from the backlogs in `tracks/`.
2. Keep each mission scoped to a one-hour chunk.
3. Execute missions in parallel lanes where possible.
4. Record evidence in `journal.md` and sync `state.json`.
5. Write or update the daily review mission.
6. Resume the next day from `handoff.md` and the review output.

## Quick Start

Create a mission:

```bash
make new-mission TITLE="AI trend scan for coding workflow" TRACK=research LANE=research ESTIMATED_HOURS=1
```

Check mission status:

```bash
make status
```

Validate the harness:

```bash
make validate
```

Run one scheduler tick manually:

```bash
make tick
```

Run one scheduler tick for a specific lane:

```bash
make tick LANE=development
```

Generate a `launchd` job definition:

```bash
make launchd-print INTERVAL_MINUTES=60 LANE=research LABEL=com.ai-train.research
```

Install a repeating `launchd` job:

```bash
make launchd-install INTERVAL_MINUTES=60 LANE=development LABEL=com.ai-train.development TICK_COMMAND='python3 scripts/my_worker.py'
```

## Design Principles

- Prefer one-hour missions with explicit acceptance criteria.
- Separate work by parallel lane so multiple agents can run without stepping on each other.
- Treat implementation and deployment work as curriculum validation, not as the end goal by themselves.
- Keep harness/process language mostly inside mission files, not inside learner-facing artifacts.
- Keep machine-readable state minimal and stable.
- Keep journal entries factual and timestamped.
- Leave a handoff every time the AI stops.
- Treat track documents under `tracks/` as source material, not transient chat context.
- Route daily closure through the `daily-review` track.

## Scheduling

The scheduler is split into two parts:

- `scripts/agent_tick.py`: picks the next actionable mission and runs one tick
- `scripts/launch_agent.py`: generates, installs, inspects, and removes a macOS `launchd` agent

`agent_tick.py` is safe by default:

- without a configured command, it only selects a mission and writes a log
- with `--command` or `AI_TRAIN_TICK_COMMAND`, it executes that command for the selected mission

Use scheduled automation carefully.

It is useful for:

- selecting the next mission
- running local worker stages
- updating state and logs

It is not, by itself, the best way to produce high-quality beginner content.
The preferred pattern is still:

1. use queue/status tooling
2. let Codex orchestrate the real content work
3. use daily review to decide the next batch

The tick runner exports these environment variables to the scheduled command:

- `AI_TRAIN_PROJECT_ROOT`
- `AI_TRAIN_MISSION_ID`
- `AI_TRAIN_MISSION_DIR`
- `AI_TRAIN_MISSION_TITLE`
- `AI_TRAIN_MISSION_TRACK`
- `AI_TRAIN_MISSION_LANE`

Examples:

```bash
python3 scripts/agent_tick.py
python3 scripts/agent_tick.py --lane research
python3 scripts/agent_tick.py --command 'python3 scripts/my_worker.py' --lane development
python3 scripts/launch_agent.py install --interval-minutes 60 --lane research --label com.ai-train.research
python3 scripts/launch_agent.py install --times 09:00,14:00 --lane aws --label com.ai-train.aws --tick-command 'python3 scripts/my_worker.py'
python3 scripts/launch_agent.py status
python3 scripts/launch_agent.py uninstall
```
